## 결정

| 항목 | 결정 |
|---|---|
| 색 계산 | HSL(채도 0.8) → OKLCH. 공개 API(`toThemeColor`, `toHueTone`, `isSameColor`)와 출력 형식(`#RRGGBB`)은 그대로 둔다 |
| 밝기 하한 | `MIN_LIGHTNESS = 0.63` 하나로 모든 색조를 덮는다. 색조별 이분 탐색은 없앴다 |
| 밝기 상한 | `MAX_LIGHTNESS = 0.93`. 2.8.0 HSL의 가장 연한 출력(체감 밝기 0.899~0.980)의 중간값이다. 더 올리면 흰 배경에서 셀이 거의 보이지 않는다 |
| 진하기 | `MAX_CHROMA = 0.15`로 제한하고, sRGB 밖이면 화면에 들어올 때까지 줄인다(gamut mapping) |
| 색조 | 슬라이더 0을 빨강으로 유지하려고 OKLCH 색조에 29°를 더한다. `toHueTone`은 그만큼 뺀다 |
| 저장 형식 | 변경 없음. 이미 저장된 사용자 지정 색은 피커를 열어도 그대로 보인다. 다만 슬라이더를 처음 움직이는 순간 새 생성기의 색으로 바뀐다(아래 "알려진 동작") |

## 배경: HSL의 문제

HSL은 모니터 RGB 값을 각도와 비율로 바꿔 쓴 것이라 사람 눈의 밝기 감각과 맞지 않는다. 같은 L 50%라도 노랑(`#FFFF00`)은 눈부시고 파랑(`#0000FF`)은 거의 남색이다.

2.8.0의 직접 선택은 셀 글자색 `#111827`과 대비 4.5:1을 지키려고 색조마다 밝기 하한을 이분 탐색으로 따로 구했다. 그 결과 같은 밝기 슬라이더 위치에서도 색조마다 체감 밝기가 달랐다.

## OKLCH

OKLCH는 OKLab 색공간의 극좌표 표현이다. OKLab은 숫자가 같은 만큼 바뀌면 눈에도 같은 만큼 바뀌어 보이도록 설계됐다.

| 축 | 뜻 | 범위 |
|---|---|---|
| L (Lightness) | 눈에 보이는 밝기 | 0(검정) ~ 1(흰색) |
| C (Chroma) | 진하기, 회색에서 얼마나 먼가 | 0(회색) ~ 약 0.37 |
| H (Hue) | 색조 각도 | 0~360°. OKLCH의 빨강은 약 29°, 0°는 분홍 쪽이다 |

글자 대비는 휘도(밝기)로 정해지므로, 밝기 축이 체감과 맞으면 대비 하한을 L 값 하나로 다룰 수 있다.

### 변환 흐름

```
OKLCH (L, C, H)
  → OKLab (L, a, b)     a = C·cos H, b = C·sin H
  → LMS                 3×3 행렬 곱 후 세제곱
  → 선형 sRGB           3×3 행렬 곱
  → sRGB 0~255          감마 보정 후 반올림
  → "#RRGGBB"
```

역변환(`toHueTone`)은 감마 해제 → 행렬 → 세제곱근(`kotlin.math.cbrt`) → 행렬 순서다. 행렬 값은 Björn Ottosson의 OKLab 정의를 따른다.

### gamut mapping

OKLCH로는 화면(sRGB)이 표현할 수 없는 색도 숫자로 만들 수 있다. 예를 들어 L 0.9의 진한 파랑은 sRGB에 없다. 그래서 선형 sRGB 각 채널이 0~1 안에 들어올 때까지 C를 이분 탐색으로 줄인다.

이 때문에 색조마다 낼 수 있는 최대 진하기가 다르다. 노랑은 밝아도 진하게 나오지만, 파랑·보라는 밝으면 연해질 수밖에 없다. 이건 OKLCH의 한계가 아니라 sRGB 화면의 물리적 한계다.

## 측정 결과

계산 조건: 색조 0~359°를 1° 간격으로, HSL은 2.8.0 코드(채도 0.8, 색조별 하한), OKLCH는 이번 값(0.63 / 0.93 / 0.15)이다. 체감 밝기는 출력 hex를 OKLab L로 되돌린 값이다.

### 같은 슬라이더 위치에서 색조별 체감 밝기 편차 [측정]

| 밝기 슬라이더 | HSL 범위 | HSL 편차 | OKLCH 범위 | OKLCH 편차 |
|---|---|---|---|---|
| 0 (가장 진함) | 0.588 ~ 0.644 | 0.056 | 0.629 ~ 0.631 | 0.003 |
| 0.5 | 0.748 ~ 0.913 | **0.164** | 0.779 ~ 0.781 | 0.003 |
| 1 (가장 연함) | 0.899 ~ 0.980 | 0.081 | 0.929 ~ 0.931 | 0.003 |

- HSL도 가장 진한 쪽은 대비 하한이 휘도를 맞춰 주기 때문에 편차가 작다. 편차가 커지는 곳은 중간 밝기다.
- OKLCH는 세 위치 모두 편차가 반올림 오차 수준이다.

### 셀 글자(`#111827`) 최저 대비 [측정]

| 밝기 슬라이더 | HSL | OKLCH |
|---|---|---|
| 0 | 4.52 | 4.67 |
| 0.5 | 7.27 | 8.25 |
| 1 | 13.01 | 14.10 |

### 진하기 상한 비교 [측정]

"필요한 하한"은 색조별로 대비 4.5를 지키는 L의 최댓값(1° 간격, hex 반올림 포함)이다. 색은 그 값에 0.005를 더한 L에서 OKLCH 색조 30°·265°·330°로 계산했다(슬라이더 각도가 아니다). 실제 앱 출력은 위 "대표 색" 표를 본다.

| 상한 | 필요한 하한 | 대표 색 (하한 + 0.005) | 판단 |
|---|---|---|---|
| 0.12 | 0.617 | `#C5695A`, `#6384CF`, `#AF6BA9` | 전반적으로 탁함 |
| **0.15** | 0.621 | `#D35F4F`, `#5B83E2`, `#B963B2` | 채택. 코드는 여유를 더 둬 0.63 |
| 0.18 | 0.625 | `#E15342`, `#5281F5`, `#C359BC` | 빨강·파랑이 강해짐 |
| 제한 없음 | 0.643 | `#FF3421`, `#5586FF`, `#E700E1` | 원색이 튐 |

## 기대와 한계

| 기대 | 결과 |
|---|---|
| 같은 슬라이더 위치에서 색조가 달라도 밝기가 고르게 보인다 | 달성. 편차 0.164 → 0.003 [측정] |
| 가장 진한 쪽의 원색 튐(마젠타 `#E119E1`)이 줄어든다 | 달성. 진하기 상한으로 `#B964B5` [측정] |
| 노랑의 올리브 느낌이 줄어든다 | **달성하지 못함.** 가장 진한 노랑은 OKLCH에서도 `#A88400`이다. 어두운 노랑은 어느 색공간에서든 올리브다 |
| 파랑·보라를 진하게 고를 수 있다 | 달성하지 못함. 어두운 글자(`#111827`)를 쓰는 한 sRGB 한계 때문에 밝은 쪽으로만 고를 수 있다 |
| 대비 계산이 단순해진다 | 달성. 색조별 하한 탐색을 상수 하나로 바꿨다 |

## 알려진 동작: 2.8.0에서 저장한 사용자 지정 색

피커는 처음 열릴 때 색을 내보내지 않으므로 저장된 색은 그대로 보인다. 하지만 슬라이더를 처음 건드리면 새 생성기가 만든 색으로 바뀌고, 그 차이가 클 수 있다. 2.8.0 HSL과 OKLCH는 같은 색을 만들 수 없기 때문이다. [측정]

| 2.8.0에서 저장한 색 | 슬라이더 위치 (2.8.0 → 이번) | 밝기를 0.01 내렸을 때 |
|---|---|---|
| `#FBFBDA` (연한 크림) | 색조 60°→78°, 밝기 1.00 | `#F2EE6D` (진한 노랑) |
| `#DAFBDA` (연한 초록) | 색조 120°→116°, 밝기 1.00 | `#ACFFAF` |
| `#EBEB4B` (중간 노랑) | 색조 60°→80°, 밝기 0.5→0.94 | `#E8E969` |
| `#E119E1` (진한 마젠타) | 색조 300°→299°, 밝기 0→0.05 | `#BC68B9` |

색조는 최대 약 20°, 밝기는 최대 약 0.45 이동한다. 직접 선택은 2.8.0에 처음 나왔고 사용 기간이 짧아 영향받는 보드가 적다고 보고 그대로 둔다. [추정]

## KMP 공통 구현

- 모든 계산은 `commonMain`의 순수 Kotlin이다. `android.graphics.Color`나 `UIColor`처럼 플랫폼마다 색공간 처리와 반올림이 다른 API를 쓰지 않아서, Android와 iOS가 같은 입력에 같은 hex를 만든다.
- 세제곱근은 `kotlin.math.cbrt`를 쓴다. `pow(x, 1.0 / 3)`은 음수 입력에서 NaN이 된다. `:core:ui:compileKotlinIosSimulatorArm64`로 Native 컴파일을 확인했다.
- 저장은 hex 문자열, 화면 표시는 기존 `String.toColor()`(expect/actual)가 맡는다.

## 검증

- **[테스트]** 색조 0~360°를 0.25° 간격으로, 밝기 0~1을 0.1 간격으로(15,851개 조합) 출력 hex의 대비 4.5 이상과 `#RRGGBB` 형식을 확인한다.
- **[테스트]** 생성기 출력의 hue/tone 왕복이 같은 색(채널 차 2 이내)으로 돌아온다.
- **[테스트]** 프리셋, 2.8.0 HSL 생성기 출력(`#E119E1`, `#87870F`, `#FBFBDA`), 회색·흰색·검정도 NaN 없이 유효한 슬라이더 위치로 바뀐다.
