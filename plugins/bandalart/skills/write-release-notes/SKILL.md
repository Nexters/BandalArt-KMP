# BandalArt 출시노트 작성

기술 구현을 설명하지 말고, 사용자가 새로 할 수 있는 일과 체감할 변화만 자연스러운 언어로 전달한다.

## 변경 근거 수집

1. 사용자가 지정한 PR, issue, commit 또는 비교 범위를 우선한다.
2. 범위가 없으면 현재 작업과 연결된 issue/PR 및 마지막 출시 이후의 변경을 확인한다.
3. 코드만 보고 기능을 확대 해석하지 않는다. 각 문장은 실제 구현이나 검증 결과로 추적할 수 있어야 한다.
4. 빌드 설정, CI, 의존성 업데이트, 내부 리팩터링처럼 사용자에게 보이지 않는 변경은 제외한다.

## 대상별 문체

- **Play Store·App Store 공개 출시노트:** 일반 사용자가 업데이트 이유를 바로 이해하도록 기능과 효용만 쓴다. 테스트 방법이나 내부 용어는 넣지 않는다.
- **Play Internal Testing:** 테스터가 새 기능을 찾을 수 있도록 진입 경로와 핵심 동작을 짧게 쓴다. 구현 방식은 설명하지 않는다.
- **TestFlight `what_to_test`:** 홍보 문구가 아니라 재현 가능한 확인 행동, 기대 결과, 회귀 확인 항목을 쓴다. 광고 모드 안내는 기존 전용 파일과 중복하지 않는다.

`Android 내부 테스트`가 Play인지 Firebase인지 불명확하면 저장소의 배포 맥락에서 확인한다. 이 스킬의 저장 경로 규칙은 Play Internal Testing에만 적용하며, Firebase 출시노트는 `deploy-android-firebase`의 경로와 절차를 따른다.

저장소의 기존 경로와 배포 설정을 먼저 확인한다. 현재 기본 경로는 다음과 같다.

- Android Internal: `androidApp/src/main/play/release-notes/{ko-KR,en-US,ja-JP}/internal.txt`
- iOS TestFlight: `fastlane/metadata/ios/what_to_test.txt`

현재 저장소에는 공개 Play Store·App Store 출시노트 파일이 정해져 있지 않다. 공개 출시노트 요청에서는 문안만 반환한다. 사용자가 파일 갱신을 요청했지만 목적지가 지정되지 않았다면 `internal.txt`나 `what_to_test.txt`를 대신 수정하거나 새 경로를 만들지 말고, 문안과 함께 저장 위치가 필요하다고 알린다.

## 사용자 언어로 바꾸기

다음 구현 용어는 원문에 필요하더라도 출시노트에서 그대로 사용하지 않는다.

- Room, migration, schema, column, DataStore, repository, presenter, outbox
- API, DI, coroutine, lifecycle, state, sync flag
- 리팩터링, 모듈화, 의존성, 빌드 파이프라인, 내부 로직

구현 명칭 대신 대상 채널에 맞춰 사용자가 경험하거나 확인할 결과로 번역한다. 같은 일일 초기화 기능도 다음처럼 달라진다.

| 대상 | 적절한 표현 |
|---|---|
| 공개 스토어 출시노트 | 매일 반복하는 목표의 완료 체크를 자동으로 새로 시작할 수 있어요. |
| Play Internal Testing | 홈의 `⋮ > 루틴 설정`에서 완료 체크를 지금 초기화하거나 매일 자동으로 초기화할 수 있어요. |
| TestFlight `what_to_test` | 기존 버전에서 업데이트한 뒤 목표 내용과 완료 상태가 유지되는지 확인해 주세요. 루틴 설정을 켠 다음 날짜가 바뀌면 완료 체크만 한 번 초기화되는지도 확인해 주세요. |

Room migration 같은 호환성 구현은 문제가 해결됐다는 별도 사용자 가치가 없는 한 공개 출시노트에서 제외한다. 내부 테스트에서는 필요할 때 `기존 목표가 유지되는지`처럼 관찰 가능한 회귀 항목으로만 바꾼다. Balloon 도입은 공개 노트에서 라이브러리명을 쓰지 않으며, Play Internal에서는 `새 기능을 쉽게 찾도록 처음 한 번 안내해 드려요`처럼 표현하고 TestFlight에서는 노출 횟수와 닫힘 상태를 확인하는 행동으로 쓴다.

## BandalArt 문체

- 한국어는 짧고 편안한 `~할 수 있어요`, `~해졌어요`, `~하지 않도록 수정했어요` 어조를 기본으로 한다.
- `신규 기능을 도입했습니다`, `고도화했습니다`, `사용성을 개선했습니다`처럼 회사·개발 보고서 같은 표현을 피한다.
- 기능 이름만 나열하지 말고 사용자가 얻는 결과를 먼저 쓴다.
- 확인되지 않은 안정성 개선, 성능 향상, 버그 수정 문구를 관성적으로 추가하지 않는다.
- 같은 내용을 여러 문장으로 반복하지 않는다. 한 항목은 한 가지 사용자 변화만 담는다.
- 제목은 대상 플랫폼에서 필요할 때만 쓰고, 본문은 짧은 문장이나 불릿으로 작성한다.

영어와 일본어는 한국어를 직역하지 말고 같은 사용자 효용과 친근한 온도를 유지한다. 제품 내 실제 메뉴명이 확인되면 그 표기를 사용한다.

## 검수

작성 후 다음을 확인한다.

1. 개발자가 아니라 처음 앱을 쓰는 사용자도 이해할 수 있는가?
2. 각 항목이 `무엇이 달라졌는지` 또는 `무엇을 할 수 있는지` 바로 말하는가?
3. 기술 용어와 구현 세부사항을 제거했는가?
4. 모든 주장이 실제 변경 범위에 근거하는가?
5. 언어별 의미와 기능 범위가 일치하는가?
6. 대상 스토어 또는 저장소 검증에서 요구하는 길이와 형식을 지키는가?

초안을 요청받으면 파일을 수정하지 않고 문안만 제시한다. 작성이나 갱신을 요청받으면 대상 플랫폼에 설정된 파일만 수정하고, 최종 답변에 사용한 변경 범위와 작성한 파일을 함께 알린다. 공개 출시노트처럼 저장소에 목적지가 없는 경우에는 위 fallback을 따른다.
